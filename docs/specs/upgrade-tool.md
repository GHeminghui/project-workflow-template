# 升级工具接口规格（`upgrade.sh` / `/upgrade`）

> **状态**：**已实现**（`scripts/upgrade.sh` + `template/.trae/commands/upgrade.md`），并有端到端测试覆盖。
> 本文为其行为契约。决策背景见 [ADR-002](../adr/002-upgrade-strategy.md)，清单数据契约见 [template-manifest.md](template-manifest.md)。

## 1. 目标与非目标

**目标**：把已建项目里的**模板文件**升到新版本，且**永不丢失用户内容**。

**非目标**：
- 不做主动通知（模板无法联系使用者，是否升级由使用者决定）
- 不处理业务代码与阶段产物——它们不在模板清单内，升级工具**不扫描**
- 不做三方合并（只判定"是否被改过"，不尝试自动合并改动）

## 2. 入口与载体

复刻 `/init-project` 已验证过的模式：**确定性脚本 + 斜杠命令包装**。

| 组成 | 位置 | 归属 |
|------|------|------|
| 脚本 | `scripts/upgrade.sh` | 开发层；由 `setup-global.sh` 复制到全局模板目录 |
| 命令文档 | `template/.trae/commands/upgrade.md` | 载荷；安装后为 `/upgrade` |

`upgrade.sh` **不属于载荷**——项目内不留副本。理由：升级需要一份"新版本"作为来源，而新版本只能来自全局模板目录或仓库；把工具放进项目只会多一份副本，却减不掉这个外部依赖。这与 `install.sh` 的处理一致。

**路径自适应载荷**：与 `install.sh` 同策略——仓库内运行时载荷为 `../template`，全局模板目录内运行时为同级目录。

三种调用场景：

| 场景 | 调用方式 |
|------|---------|
| 使用者（TRAE 内） | 敲 `/upgrade`，由 AI 执行 `$HOME/.trae/templates/project-workflow/upgrade.sh "$(pwd)"` |
| 使用者（终端） | `bash ~/.trae/templates/project-workflow/upgrade.sh [目标目录]` |
| 维护者（仓库内） | `bash scripts/upgrade.sh <目标目录>` |

## 3. CLI 契约

```
bash upgrade.sh [目标目录] [选项]

选项:
  --apply    按预览结果落盘（默认只读，不写任何文件）
  --force    连「被改过」的模板文件也覆盖；覆盖前备份为 <文件>.bak
  -h, --help 显示帮助
```

- **默认即只读**。不带 `--apply` 时脚本不写入任何文件，可安全反复运行。
- **不使用交互式询问**。脚本永不调用 `read` 或等待输入——它既被人调用，也被 AI 通过斜杠命令调用；交互式提示会让后者卡死。人机确认由 `/upgrade` 命令文档承担：先跑只读预览，展示报告，征求用户确认，确认后再带 `--apply` 执行。
- `--force` 与 `--apply` 可叠加：`--apply --force`。
- 单独使用 `--force`（不带 `--apply`）时，预览报告应显示"若加 `--force` 将覆盖哪些文件"，便于用户预判。
- 由于版本相同时会短路（§5），`--force` **实际只在「版本跃迁」期间有意义**——那正是唯一需要决定"如何对待被改过文件"的时刻。版本已一致时不存在跃迁，也就无从触发覆盖。（`--force` 的另一个用途见 §3.1。）

### 3.1 目标目录准入检查

升级只作用于**模板项目**。目标目录必须至少满足下列一条，否则视为误传目标并**拒绝执行**（退出码 `2`，不写入任何文件）：

- 存在 `PROJECT_STATE.json`（正常项目；老项目也一定有它）
- 存在 `.trae/template-manifest.json`（项目侧基线）

「不像项目」时的行为：

- 只读预览与 `--apply` **都**被拒绝——门禁在扫描之前，不存在"预览安全、落盘危险"的割裂
- 若确认要在该目录执行（例如手工修复过目录结构），显式加 `--force` 放行

> 加这道门禁的原因：目标目录默认 `.`（见上），一旦把仓库根或任意目录误当成项目，
> `--apply` 会把整套载荷文件写进去。故默认**拒绝**而非仅警告。

## 4. 文件状态 → 动作（核心语义）

判定输入来自项目内的模板清单（`.trae/template-manifest.json`）与逐文件 sha256。完整判定依据见 [template-manifest.md §8](template-manifest.md)。

| 项目内文件状态 | 预览标记 | 默认（`--apply`）动作 | 加 `--force` 后 |
|---------------|---------|---------------------|----------------|
| 与**新载荷**哈希一致（已是最新） | （只计数） | 不动 | 不动 |
| 与**项目基线**哈希一致（未改动） | `~` | **覆盖**为新版 | 同左 |
| 两份哈希都不一致（被改过） | `!` | **跳过**，列入「待合并」 | **覆盖**，覆盖前备份为 `.bak` |
| 文件不存在（缺失） | `+` | **恢复**为新版 | 同左 |
| 清单标 `create-only` | `=` | **永不整体覆盖**（仅字段级更新，见下） | 同左 |
| 不在清单中 | 不扫描 | 不触碰 | 不触碰 |

### 4.1 判定依据：必须同时比对两份清单

「是否被用户改过」**不能只跟新版比**——新版与用户的版本本来就应当不同。判定必须用两份哈希：

| 比对 | 含义 | 结论 |
|------|------|------|
| 项目文件 == **新载荷**清单的 `sha256` | 内容已等于新版 | 已是最新，无需处理 |
| 项目文件 == **项目内基线清单**的 `sha256` | 仍是安装时的原样 | 未被改动，可安全覆盖 |
| 两者都不等 | 用户在其上做过修改 | 被改过，默认不覆盖 |

这正是模板清单需要同时充当「载荷声明」与「项目侧基线」两个角色的原因（见 [template-manifest.md](template-manifest.md) §4）。

### 4.2 缺少基线清单时（老项目）

若项目内没有 `.trae/template-manifest.json`（例如由早于 v0.2.0 的版本安装），则**无法判定任何文件是否被改动**。此时：

- **已存在的模板文件一律按「被改过」处理**，默认不覆盖，列入「待合并」
- 缺失的文件照常恢复
- 报告须显式说明原因（「缺少基线清单，无法判定改动」）
- 需要覆盖时只能走 `--force`

首次带 `--force` 完成升级后，项目内即写入基线清单，**后续升级恢复精确判定**。这是老项目的一次性代价。

### 4.3 升级成功后的版本推进

动作落盘后还必须推进两个标记，否则下次升级会重复判定：

- **替换项目内清单**为新载荷的清单——基线前进到新版本
- **字段级**更新 `PROJECT_STATE.json` 的 `template_version`——**只改这一个字段，绝不整体覆盖该文件**（它是用户数据，承载项目进度）

若 `PROJECT_STATE.json` 缺少 `template_version` 字段，则新增该字段，同样只做字段级写入。

**设计原则：默认行为永远不会丢失用户内容。**

由此推出两条具体规则：

1. **缺失文件默认恢复**。恢复不构成数据损失（文件本就不存在），而缺文件会导致工作流缺件。仅 `create-only` 例外——它承载用户数据，缺失时由安装流程按首次写入处理，升级工具不擅自重建。
2. **覆盖「被改过」的文件必须显式授权**。用户改动是唯一会被覆盖行为毁掉的东西，因此只有在 `--force` 下才覆盖，且覆盖前必须落一份 `.bak`。

**不写 `.new` 文件。** 新版内容已完整存在于全局模板目录，用户可直接与之 diff 后手工合并；在项目里另存 `.new` 只会产生需要清理的垃圾。

## 5. 报告格式

预览与应用使用同一份报告结构，仅标题行区分模式：

```
==> 项目: /Users/me/code/my-app
==> 项目模板版本: 0.1.2
==> 模板版本:     0.2.0
==> 模式: 只读预览（未写入任何文件）

  覆盖   2 个（模板文件，未被改动）
    ~ .trae/hooks.json
    ~ 00-discovery/README.md
  恢复   1 个（模板文件缺失）
    + .trae/scripts/inject_status.py
  待合并 1 个（你改过，默认不覆盖）
    ! AGENTS.md
  不动   1 个（用户数据）
    = PROJECT_STATE.json
  未变更 10 个

  下一步: bash upgrade.sh --apply
  需要连「待合并」的文件一起覆盖时: bash upgrade.sh --apply --force
```

规则：
- 按「覆盖 / 恢复 / 待合并 / 不动」分组列出**文件路径**，不列哈希（人不需要看）
- 「未变更」只给计数，不逐个列出，避免噪音
- 版本相同时输出「已是最新（0.2.0）」并正常退出，不做其他检查
- 项目侧清单缺失或 `PROJECT_STATE.json` 无 `template_version` 时，视为**版本未知**（老项目），报告需显式说明，并按第 4 节矩阵照常给出计划

> ⚠️ **该短路的正确性依赖一条外部约束**：载荷（`template/`）一有改动就必须推进 `VERSION`。
> 否则「载荷内容已变、版本号未变」会让升级被误判为已是最新而**静默失效**。
> 这条约束记录在 [CONTRIBUTING.md 的发布小节](../../CONTRIBUTING.md)。

## 6. 退出码

参照 `diff` 的惯例，让自动化与 AI 能据退出码判断状态：

| 码 | 含义 |
|----|------|
| `0` | 无待升级项——已是最新；或 `--apply` 后已完全对齐（不含待合并项） |
| `1` | 存在待处理项——预览模式下发现差异；或 `--apply` 后仍有「待合并」文件需人工介入 |
| `2` | 执行错误——参数非法、目标目录不存在、**目标目录不像模板项目（未加 `--force`，见 §3.1）**、载荷清单缺失、python3 不可用等 |

## 7. 使用顺序（必须写进文档）

升级源是**全局模板目录**，因此标准流程是两步：

```
1. 重新运行 setup-global.sh        # 从 GitHub 取得新版载荷到 ~/.trae/templates/project-workflow/
2. 在项目内运行 /upgrade            # 把项目升到新版
```

若跳过第 1 步，第 2 步会报「已是最新」——因为全局模板仍是旧版。这一顺序必须在使用者文档中显式说明，否则会产生"为什么升不动"的困惑。

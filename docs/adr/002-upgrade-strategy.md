# ADR-002: 模板升级策略

- **状态**：已采纳
- **日期**：2026-09-26
- **决策者**：模板维护者

## 背景

模板采用「复制式脚手架」分发：`scripts/install.sh` 把 `template/` 载荷复制进用户项目，此后项目与上游**没有任何链接**。这带来三个已确认的问题。

### 问题一：没有版本锚点

`PROJECT_STATE.json` 没有模板版本字段。载荷中唯一的 `version` 是 `.trae/hooks.json` 里的 `"version": 1`，那是 **TRAE Hook 配置的 schema 版本，不是模板版本**。

后果：项目无法知道自己由哪个模板版本创建，也就无法判断「是否需要升级」。

### 问题二：`install.sh -f` 会造成数据丢失

`PROJECT_STATE.json` 是载荷中**唯一兼具「模板文件」与「用户数据文件」双重身份**的文件。而 `install.sh -f` 无差别覆盖全部载荷文件；事后脚本只回写 `project_name` / `created_at` / `last_updated`，**不恢复** `current_stage`、清单勾选与产物列表。

实测（安装 → 模拟推进到设计阶段 → 再次 `install.sh -f`）：

| 字段 | 推进后 | `-f` 之后 |
|---|---|---|
| `current_stage` | `design` | `discovery`（回退） |
| discovery `status` | `done` | `in_progress`（回退） |
| 清单勾选数 | 3 | 0（全丢） |
| `deliverables` 数 | 2 | 0（全丢） |

用户的真实产物文件（如 `00-discovery/research.md`）因不在载荷清单内而**未被删除**，但状态被重置后它们成了**孤儿**——状态与磁盘不一致，下次会话 Hook 注入的状态会让 AI 误判项目回到起点。

（现有 `tests/test_install.sh` 第 5 节只断言 `--force` 覆盖 `AGENTS.md`，从未检查 `PROJECT_STATE.json`，故此缺陷未被测试覆盖。）

### 问题三：没有安全升级路径

- `/init-project` 调用 `install.sh` 时**不带 `-f`**，对已存在文件一律 `[跳过]`。所以它能「补齐缺失文件」，但**不能更新已有文件**。
- 能覆盖文件的 `-f` 又不安全（见问题二）。

结论：使用者想升级，**目前没有安全的做法**。

### 约束

- TRAE 要求 `AGENTS.md` 与 `.trae/` 位于**项目内**并作为项目规则加载，因此无法改为纯引用式分发。
- 模板必须对使用者保持**技术中立、轻量、可离线**。
- 项目必须保持**自包含**——使用者的项目可能被独立纳入自己的 git 管理。
- `AGENTS.md` 已确立「状态单一数据源」原则，不可破坏。
- 模板无法主动联系使用者（发布渠道是 GitHub Release，无回连能力）。

## 决策

保留复制式分发，并在其上建立**显式版本锚点 + 声明式文件边界 + 默认只读的升级流程**。

### 1. 版本锚点落在 `PROJECT_STATE.json`

新增 `template_version` 字段，值为模板语义化版本，与 `CHANGELOG.md` 的版本段和 git tag 对齐。

理由：`AGENTS.md` 已确立「状态单一数据源」，AI 与脚本都从 `PROJECT_STATE.json` 读取进度；版本属于同一类元数据，放在一起可避免再引入一个并行的事实源。

### 2. 文件边界声明化

引入一份**随载荷分发**的模板清单文件，记录模板文件列表以及**安装时每个文件的 sha256**，取代 `install.sh` 中硬编码的复制列表。

（备选：只记文件名不记哈希——无法自动判定「是否被改过」；维持脚本内硬编码列表——文件边界仍是隐式的。两者均未采纳。）

升级时据此把项目内文件分为三类：

| 类别 | 判定 | 升级时处理 |
|------|------|-----------|
| 模板文件（未被改动） | sha256 与清单一致 | 可直接覆盖 |
| 模板文件（用户改过） | sha256 不一致 | **不覆盖**，输出 diff 提示 |
| 用户数据 | 不在清单内 | **永不触碰** |

### 3. `PROJECT_STATE.json` 明确归为「用户数据」

将其从「全量覆盖」集合中**永久剥离**：

- 文件**不存在**时，才写入初始模板内容；
- 文件**已存在**时，脚本只允许做**字段级**最小更新（如 `template_version`、`last_updated`），**绝不整体覆盖**。

### 4. 升级默认「只看不改」

升级工具默认只输出差异报告（dry-run），不写入任何文件；需显式确认才落盘。落盘时对被用户改过的文件输出为 `.new` 或先备份为 `.bak`，而非静默覆盖。

（备选：自动覆盖 sha256 未变的模板文件，更省事，但会在使用者不知情时修改其项目，与「可预测」相冲突，未采纳。）

### 5. 不做主动通知

模板无法也无意主动联系使用者。是否升级、何时升级由使用者决定；使用者通过重新运行 `scripts/setup-global.sh` 刷新全局模板（该脚本会 `rm -rf` 全局模板目录后重装，已是安全的刷新路径）。

### 6. `--force` 语义收紧

保留 `--force`，但明确它**只作用于模板文件**，不再触碰用户数据；并在 `--help` 与文档中标注其影响范围。

## 备选方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| 复制式 + 版本锚点 + 安全升级（**采纳**） | 项目自包含、可离线；风险可控；改动集中在脚本层；与既有设计一致 | 需维护清单与哈希；不解决「想不起来升级」 |
| 仅修 `-f` 的数据丢失，不做版本锚点 | 改动最小，立刻消除数据丢失 | 使用者仍无法判断是否过期，升级仍靠人工摸索 |
| 改为引用式（项目只放薄壳，模板集中于全局目录） | 升级天然即时，无需复制 | **不可行**：TRAE 需项目内存在 `AGENTS.md`/`.trae/`；且全局模板一变，老项目行为突变，破坏可预测性 |
| 用 git submodule / subtree 承载模板 | 可追踪上游、可复用 git 合并 | 要求使用者具备 git 能力，与「技术中立、轻量」冲突；目录嵌套破坏 `AGENTS.md` 必须位于项目根的要求 |
| 升级时一律 `git merge` 上游 | 复用成熟的三方合并 | 使用者项目未必是 git 仓库；模板文件与业务文件混存，冲突面过大 |

## 后果

- **正面影响**
  - `PROJECT_STATE.json` 不再可能被升级流程破坏，消除已确认的数据丢失风险。
  - 使用者能知晓自己的模板版本，进而判断是否需要升级。
  - 升级有明确、可预览、可回退的路径。
  - 文件边界由声明清单固化，不再依赖脚本里的隐式列表。

- **负面影响**
  - 载荷将新增一个清单文件，使用者会看到。
  - `PROJECT_STATE.json` 增加字段，需处理老项目「无该字段」的兼容（视为「版本未知」）。
  - 升级仍是人工触发，不解决「忘记升级」的问题。
  - 哈希比对只能判断「是否被改过」，无法判断改动是否实质影响兼容性。

- **后续动作**
  1. **紧急且独立**：修 `scripts/install.sh`，使 `-f` 不再整体覆盖 `PROJECT_STATE.json`。
  2. `PROJECT_STATE.json` 增加 `template_version`，`install.sh` 写入当前模板版本。
  3. 引入模板清单文件，`install.sh` 改为按清单复制。
  4. 新增升级工具（默认 dry-run），并在 `template/.trae/commands/` 下提供入口。
  5. 更新 `docs/design.md`（把「升级」从设计空白变为明确策略）、`docs/architecture.md`、`CONTRIBUTING.md`。
  6. 补测试：`tests/test_install.sh` 增加「`-f` 不得破坏 `PROJECT_STATE.json`」的断言。
  7. `CHANGELOG.md` 记录本决策及其实现。

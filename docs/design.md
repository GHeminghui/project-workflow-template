# 设计原理

本文说明**为什么**这套模板这样设计。改动模板前请先读本文，避免破坏原有设计意图。

## 目标

让「按流程做事」这件事**不需要人反复提醒 AI**：

1. 新项目自动套用四阶段流程
2. 每次会话 AI 自动知道当前处于哪个阶段、下一步做什么
3. 阶段推进有门控，不能跳步

## 三条设计主线

### 主线一：规范与状态分离

- **规范**（不变的东西）→ `template/AGENTS.md`
- **状态**（一直在变的东西）→ `template/PROJECT_STATE.json`

之所以分开，是因为两者加载方式和变更频率完全不同：

| | 规范（AGENTS.md） | 状态（PROJECT_STATE.json） |
|---|---|---|
| 变更频率 | 极低 | 每次推进阶段、勾选任务 |
| 加载方式 | TRAE 作为项目规则自动注入 | 由 Hook 脚本读取后注入 |
| 谁维护 | 模板维护者 | AI + 用户 |

### 主线二：为什么用 Hook 而不是只靠 AGENTS.md

如果只靠 `AGENTS.md`，AI 只能知道「流程是什么」，**不知道「现在做到哪了」**。
`SessionStart` Hook 补上了后者：会话一开始就把 `PROJECT_STATE.json` 渲染成一段状态摘要注入上下文。

这解决了最核心的痛点——**跨会话的记忆恢复**。变量、上下文、AI 的"记忆"都会随会话结束而消失，但状态文件不会。

### 主线三：状态用 JSON 而非 Markdown

用 JSON 存状态，是为了让**脚本可读可写**：

- `inject_status.py` 能稳定解析并渲染
- 未来可扩展自动化（统计、报表、CI 校验）
- 结构明确，AI 解析不易出错

代价是人工阅读不如 Markdown 直观，但状态主要由 AI 维护，人通过 `/status` 查看即可。

## 阶段门控的设计

`/advance` 在推进前会校验当前阶段 `checklist` 是否全部 `done`，未完成则拒绝。
这实现了「准入准出」中的**准出**：保证阶段产物齐全才进入下一阶段。

选择用 checklist 布尔值而非复杂规则，是因为：
- AI 判断"某项是否完成"本身有弹性，硬规则难落地
- 布尔勾选让 AI 和用户都有明确的判断依据
- 结构简单，不易出错

## 双层仓库结构的原因

早期版本把「用户载荷」和「开发文档」混在仓库根目录，导致一个真实问题：

> 当维护者在 TRAE 中打开仓库想优化模板时，TRAE 会自动加载根目录 `AGENTS.md`，AI 误以为自己在做一个四阶段业务项目，跑去读占位的 `PROJECT_STATE.json`，上下文错位。

于是拆成两层：
- **开发层**（仓库根）：给维护者与 AI 的指引
- **载荷层**（`template/`）：给最终用户的内容

两者物理隔离，各自加载各自的内容，互不干扰。决策细节见 `adr/001-two-layer-structure.md`。

## 非目标

- **不做**复杂的权限/审批系统（保持轻量）
- **不做**与具体语言/框架绑定（模板必须技术中立）
- **不做**多阶段并行（刻意保持线性，简单可预测）

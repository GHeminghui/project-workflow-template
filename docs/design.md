# 设计原理

本文说明**为什么**这套模板这样设计。改动模板前请先读本文，避免破坏原有设计意图。

## 目标

让「按流程做事」这件事**不需要人反复提醒 AI**：

1. 新项目自动套用四阶段流程
2. 每次会话 AI 自动知道当前处于哪个阶段、下一步做什么
3. 阶段推进有门控，不能跳步

## 三条设计主线

### 主线一：规范与状态分离

- **规范**（不变的东西）→ `template/AGENTS.md`
- **状态**（一直在变的东西）→ `template/PROJECT_STATE.json`

之所以分开，是因为两者加载方式和变更频率完全不同：

| | 规范（AGENTS.md） | 状态（PROJECT_STATE.json） |
|---|---|---|
| 变更频率 | 极低 | 每次推进阶段、勾选任务 |
| 加载方式 | TRAE 作为项目规则自动注入 | 由 Hook 脚本读取后注入 |
| 谁维护 | 模板维护者 | AI + 用户 |

### 主线二：为什么用 Hook 而不是只靠 AGENTS.md

如果只靠 `AGENTS.md`，AI 只能知道「流程是什么」，**不知道「现在做到哪了」**。
`SessionStart` Hook 补上了后者：会话一开始就把 `PROJECT_STATE.json` 渲染成一段状态摘要注入上下文。

这解决了最核心的痛点——**跨会话的记忆恢复**。变量、上下文、AI 的"记忆"都会随会话结束而消失，但状态文件不会。

### 主线三：状态用 JSON 而非 Markdown

用 JSON 存状态，是为了让**脚本可读可写**：

- `inject_status.py` 能稳定解析并渲染
- 未来可扩展自动化（统计、报表、CI 校验）
- 结构明确，AI 解析不易出错

代价是人工阅读不如 Markdown 直观，但状态主要由 AI 维护，人通过 `/status` 查看即可。

## 阶段门控的设计

`/advance` 在推进前会校验当前阶段 `checklist` 是否全部 `done`，未完成则拒绝；此外还会**逐项核对已勾选项的 `artifact` 是否真实存在**，缺失时列出并请用户确认——只检查勾选会让空目录也能推进。
这实现了「准入准出」中的**准出**：保证阶段产物齐全才进入下一阶段。

**准入**则不做机器校验：它是模板的**静态约定**（如「设计阶段已通过 `/advance` 推进」「已明确需求清单与约束条件」），写在对应阶段目录的 `README.md` 里，对同一阶段的所有项目都相同，因此不进 `PROJECT_STATE.json`——后者只存随项目变化的状态。`validate.sh` 第 12 节只保证每个阶段 README 都写明了准入条件，不校验其内容。这也修正了早期 `AGENTS.md` 的一句歧义表述（曾写「准入准出以 `checklist` 为准」，但 checklist 实际只编码准出）。

选择用 checklist 布尔值而非复杂规则，是因为：
- AI 判断"某项是否完成"本身有弹性，硬规则难落地
- 布尔勾选让 AI 和用户都有明确的判断依据
- 结构简单，不易出错

## 双层仓库结构的原因

早期版本把「用户载荷」和「开发文档」混在仓库根目录，导致一个真实问题：

> 当维护者在 TRAE 中打开仓库想优化模板时，TRAE 会自动加载根目录 `AGENTS.md`，AI 误以为自己在做一个四阶段业务项目，跑去读占位的 `PROJECT_STATE.json`，上下文错位。

于是拆成两层：
- **开发层**（仓库根）：给维护者与 AI 的指引
- **载荷层**（`template/`）：给最终用户的内容

两者物理隔离，各自加载各自的内容，互不干扰。决策细节见 `adr/001-two-layer-structure.md`。

## 升级策略：复制式分发 + 显式版本锚点

模板采用**复制式脚手架**分发：`install.sh` 把载荷复制进用户项目，此后项目与上游没有任何链接。这换来了项目自包含、可离线、可被使用者独立纳入自己的 git 管理；代价是上游改进**不会自动触达**已建项目。

这不完全是取舍，也受平台约束：TRAE 需要项目内存在 `AGENTS.md` 与 `.trae/` 作为项目规则加载，因此**纯引用式分发在平台上不可行**。

为了让「想升级」这件事有安全路径，在复制式之上补了三件东西：

| 机制 | 载体 | 作用 |
|------|------|------|
| 版本锚点 | `VERSION` → 清单与 `PROJECT_STATE.json` 的 `template_version` | 让项目能判断自己是否过期 |
| 文件边界声明化 | `template/.trae/template-manifest.json`（含逐文件 sha256） | 让升级能区分「未改动的模板文件」「被用户改过的模板文件」「用户数据」 |
| 默认只读 | 升级工具（待实现）默认 dry-run | 消除「升级即破坏」的风险 |

**关键约束**：`PROJECT_STATE.json` 与模板清单都是**双重身份文件**——既是载荷的一部分，又承载项目侧的数据/基线。因此二者都**永不参与整体覆盖**。

这条约束不是推演出来的，源自一次真实事故：`install.sh --force` 曾把 `PROJECT_STATE.json` 重置为初始值，清空用户已推进的阶段、清单勾选与产物记录，而磁盘上的产物文件成了孤儿。

决策见 [ADR-002](adr/002-upgrade-strategy.md)，清单格式见 [specs/template-manifest.md](specs/template-manifest.md)。

## 项目生命周期与终态

阶段链是单向的，但项目本身需要**明确的端点**，否则「调研判定 No-Go」与「全流程完成归档」两种情形无处表示：

| `project_status` | 含义 | 由谁设置 |
|---|---|---|
| `active` | 进行中 | 初始值 |
| `rejected` | 调研阶段判定 No-Go，流程终止 | `/advance` 在 discovery 阶段确认 No-Go 后 |
| `archived` | 四阶段全部完成并归档 | `/advance` 在 operations 完成后经用户同意 |

这样既保留了线性（不给阶段链加回路），又让「已终止」与「已完成」成为可表达、可被 Hook 识别的状态——Hook 在非 `active` 时只提示状态、不再推动阶段。

## 非目标

- **不做**复杂的权限/审批系统（保持轻量）
- **不做**与具体语言/框架绑定（模板必须技术中立）
- **不做**多阶段并行（刻意保持线性，简单可预测）
- **不做**阶段回退与迭代循环（同上；迭代方式见 `template/AGENTS.md` 的「关于迭代」）
- **不做**需求裁剪（N/A）机制——若允许「跳过某项准出」，门控就失去确定性
